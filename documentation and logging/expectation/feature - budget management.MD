### 2026-09-09 — "Account Cost Table" cost-increase question

User saw staging dashboard screenshot: Account Cost Table showing `Account Cost` vs `Account Increased Cost` columns, all higher in the second column, asked why cost is increasing.

**Root cause (verified live on staging, read-only):**
Not real AWS billing growth. `Account Increased Cost` = `Account Cost * (1 + percentage_increase/100)`, computed in `budget_tracker/fetch_cost_service.py::_apply_percentage_increase` (line ~50). `percentage_increase` is a per-`Budget` field (`budget_tracker/models.py:127`, nullable, no model default — defaults to 0 only if null, per `_validate_percentage_increase`, fetch_cost_service.py:36-47).

Queried live `Budget` table on staging (`codly_backend_staging` container, read-only Django shell): **every existing Budget row has `percentage_increase = 10.00`**, set explicitly per-budget (no hardcoded backend default, no frontend pre-fill found in `BudgetForm.tsx`). Math confirms exact 10% multiplier on all 4 screenshot rows (530.30→583.33, 448.41→493.25, 414.67→456.14, 20.02→22.02, total 1413.40→1554.74).

**Conclusion:** this is the chargeback/budget-markup feature working as designed — "Increased Cost" is a projected/billback figure (e.g. overhead or margin markup for internal chargeback), not a cost anomaly. The dashboard doesn't label the column as "with X% markup applied," which is a UX/labeling gap worth flagging, not a backend bug.

**Not yet checked:** whether the "10%" figure is deliberate business policy across all customers or accidental copy-paste when these test budgets were created (all 4 staging budgets happen to share the same 10.00 value). Ask user/TL if that's suspicious.

### 2026-09-09 — "Is something wrong in cost distribution" — staging log check

User asked to check staging log for cost-distribution problems. No live tracebacks/errors in 48h of `codly_backend_staging` logs for `distribut|budget_tracker|shared_cost|untagged` — today's displayed numbers aren't actively corrupted. But found two real correctness gaps in `distributed_shared_cost_service.py`, both verified live:

**Gap 1 — no DB-level duplicate protection (visible in the staging log itself).** Startup log shows `budget_tracker.BudgetAccounts: (models.W036) MySQL does not support unique constraints with conditions.` (same for `TagBudget`). Both models declare conditional `UniqueConstraint`s (models.py ~301-322 for `BudgetAccounts`, ~416-435 for `TagBudget`) — one unique-per-budget, one unique-per-chargeback, each gated by a `condition=models.Q(...)`. MySQL doesn't support partial/conditional unique indexes, so Django silently never creates these constraints in the DB. Queried live staging DB: **0 duplicates today** (15 rows each table, clean) — but nothing stops a retried request / double-submit / race condition from inserting a second row for the same `(budget, account)` or `(chargeback, account)`, which would double-count that account's cost anywhere the rows are summed/iterated for distribution. Latent risk, not yet triggered.

**Gap 2 — dead validator, no server-side reconciliation for FIXED_PERCENTAGE / FIXED_VALUE splits.** `_validate_distribution_block` (distributed_shared_cost_service.py ~181-269) enforces FIXED_PERCENTAGE rows sum to 100 and FIXED_VALUE rows sum to the fee amount — but it's **never called anywhere** (grepped whole repo). The four live distribution entry points (`calculate_distribute_support_cost`, `calculate_distribute_operation_management_cost`, `calculate_distributed_shared_cost`, `calculate_distribute_untagged_cost`) apply each row's `add_cost`/percentage with zero cross-row total check. Frontend `TagBudgetForm.tsx` does enforce sum=100 / sum=fee before submit (lines ~4134-5295), so normal UI use is protected — but any direct API call, retry, or a frontend bug bypasses it entirely and distributed totals silently stop reconciling with the input cost/fee.

Neither gap is causing today's numbers to be wrong. Both are backend robustness/defense-in-depth holes worth fixing.

### 2026-09-09 — Real bug: "Account Selection" checkboxes on Create Tag Budget page (the one in the screenshot)

User pointed at `http://127.0.0.1:3004/admin/budget_tracker/create?type=tag&mode=budget` directly — the checkboxes under "Cloud Provider" → "Account Selection" (AWS Master/Production/Test Account, LogArchive) were unclickable. **This is a different block than the "Get Cost" fix above** — that one lives further down the flow (Account Cost Table, after fetching); this one is the very first account picker on the page, `TagBudgetForm.tsx` ~line 3330.

Root cause, structurally deeper than the earlier decorative-checkbox bugs: `checked` was hardcoded true for every rendered account (`selectedCloudAccountIdSet.has(account.id)` — always true by construction, since these are exactly the accounts of a selected cloud), `disabled` was hardcoded, AND even if disabled were removed, a self-syncing `useEffect` (~2279) forces `account_ids` back to "every account under every selected cloud" on every render — so per-account deselection was architecturally impossible while its cloud stayed checked, not just a missing click handler.

**Fix:** added `manuallyDeselectedAccountIds` (Set<number>) state + `toggleAccountSelection`. The sync effect now computes `nextIds` as `(preserved ∪ selectedCloudAccountIds) − manuallyDeselectedAccountIds` instead of a blind union. A second effect prunes an id out of `manuallyDeselectedAccountIds` once it falls out of `selectedCloudAccountIdSet` (i.e. its cloud got unchecked), so re-checking that cloud later starts everyone selected again rather than leaving a stale exclusion. Checkbox `checked` now reads `!manuallyDeselectedAccountIds.has(account.id)`, `onCheckedChange` wired to the toggle, `disabled` removed. Typecheck clean.

This is the fix that actually answers "why am I not able to select account" — the earlier per-cloud "Get Cost" button addition was a real but separate feature (re-fetch one account's cost after a cloud-wide fetch), not what was shown in the screenshot.
