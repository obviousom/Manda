Where AWS and Azure actually diverge

Pure classification-criteria gaps only — not policy-targetability, not the dashboard's page layout. Six places where the same resource kind gets judged by genuinely different rules depending on which cloud it's in, ranked by what breaks if you ignore it.

1

Unattached disks / volumes

Missing entirely
AWS

Scores unattached EBS volumes — age, tags, encryption, size. Shipped this session.

Azure

Does not score this resource kind at all. No dashboard page produces a verdict on it.

Why it matters: an unattached Azure managed disk billing every month is invisible to the waste dashboard, full stop — not misjudged, not deprioritized, never evaluated.

azure_disks has a WASTE_RESOURCE_SCHEMA entry (used by the agent-chat tool) but no PageSpec in policy_map.py — never wired to a dashboard scan path.
2

Serverless & containers

Missing entirely
AWS

Three dedicated pages: Lambda functions, ECR images, EFS file systems — each scored.

Azure

Zero equivalents. No Functions, no Container Registry, no Azure Files.

Why it matters: not a thin implementation to sharpen — an entire category of Azure spend has no waste-detection story yet.

3

AMI / Image in-use safety net

Live-deletion risk
AWS

An AMI referenced by a live launch template, ASG, or running instance is force-downgraded to REVIEW — never auto-scored WASTE.

Azure

No equivalent check. An actively-used custom image can score straight to WASTE.

Why it matters: the only gap on this list where getting it wrong means recommending deletion of something actually in use.

grep confirmed live — azure_ami_provider.py:15 carries only a comment ("image older than review_days but may be in use"), no actual reference check. My recommended starting point.
4

Retention-tag exemption

Resolved
AWS

Stopped EC2 + unattached EBS volumes both honor retention/backup/"do not delete" tags — short-circuits to KEEP.

Azure

Deallocated VMs now honor the same tags — mirrors AWS's exemption exactly, same short-circuit to KEEP.

Why it mattered: an Azure VM tagged "keep forever" got the exact same verdict as an untagged one. The tag did nothing.

Live testing during the fix caught a second bug: Azure has no "Name" tag convention like AWS EC2, so a real VM named DO-NOT-DELETE-ONLY-STO-RUNBOOK-TESTING was still scoring TERMINATE — the check now also reads the VM's actual resource name, not just its tags.

5

Running-instance scoring depth

Resolved
AWS

Env-aware bands (dev/staging ≥50 TERMINATE, prod ≥80) and non-prod scheduling escalation.

Azure

Now uses the same env-aware bands, matched number-for-number to AWS's thresholds.

Why it mattered: a prod Azure VM got terminated at the same score a dev AWS instance would be — no environment awareness at all.

Correction from the original write-up: Azure's scheduling-escalation check already existed before this fix (same non-prod >9h/day logic AWS has) — that part was never actually missing. Only the threshold-banding half was real. AWS's memory-bound override (CPU<20%/memory>70%) is deliberately not replicated — Azure has no memory metrics without the Monitor Agent, so the check would always be false. A permanent asymmetry, documented in code, not a bug.

6

Elastic IP / Public IP

Reverse — AWS behind
AWS

Binary WASTE/HEALTHY rule. No numeric score, no REVIEW tier at all.

Azure

Full scored action-field with a REVIEW tier — more nuanced verdict.

Why it matters: the one item here where Azure is the more mature implementation. Lowest urgency, but worth closing for real parity.
