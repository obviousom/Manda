Rule_Engine — P001 through P012

Spec's core decision tree, in priority order. "Matched" means the exact business condition is checked in code today; "Partial" means a related mechanism exists but doesn't cover the spec's full condition; "Missing" means no code path checks this at all — the resource just falls through to plain score-based classification.

RuleSpec conditionStatusWhat's actually in code
P001 Retention / do_not_delete / legal hold → KEEP, ignore score Partial Implemented for stopped/deallocated instances on both clouds (AWS _classify_stopped, Azure _score_deallocated_vm — fixed today). Not checked for running instances on either cloud — a running dev box tagged do_not_delete=yes gets no protection.
P002 HA/DR/standby confirmed → KEEP Missing No HA/DR/standby tag detection exists anywhere in either provider file. Scenario 5 and 18 in the spec's own test matrix (DR standby, HA node) would both misclassify as WASTE/REVIEW today.
P003 Scheduled/batch workload, low utilization outside window → KEEP Missing Code has the opposite check — flags a non-prod instance running too many hours/day (REVIEW_SCHEDULE, both clouds). The spec's protection for a batch job legitimately idle outside its schedule doesn't exist.
P004 Recently created / insufficient lookback → REVIEW Missing No age-of-resource or telemetry-history gate before scoring on either cloud. A VM created 3 days ago is scored exactly like one with 90 days of history.
P005 Missing/stale required metrics → REVIEW, don't score as evidence Partial AWS already got the scoring half right on its own — _compute_waste_score() only ever adds points for a metric it actually has, missing data contributes exactly 0. Azure was adding +10 for missing CPU data; fixed today to also contribute 0. Neither cloud has a staleness/freshness check (STALE_DATA_HOURS) or a hard REVIEW override — a resource with zero data still falls through to whatever score its other signals produce, rather than being forced to REVIEW outright.
P006 CPU low + memory>70% → cap at REVIEW Partial AWS has this almost exactly (CPU<20% and memory>70% → forced MONITOR). Azure cannot implement this — no memory metrics without the Azure Monitor Agent, documented as a permanent gap in this session's PR #2033.
P007 Seasonal/peak workload detected → REVIEW, extend lookback Missing No seasonality/peak-vs-average analysis anywhere. All scoring uses a flat 7-day average window on both clouds.
P008 ASG/VMSS group context → REVIEW, evaluate at group level Missing Neither provider checks Auto Scaling Group or VM Scale Set membership. Every instance is scored as a fully independent resource.
P009 Prod + high score but no independent evidence → REVIEW Partial Prod gets a higher raw threshold (80 vs. 50/70 for TERMINATE) on both clouds — a blanket shift, not the spec's "require independent corroborating evidence" check. No separate evidence-count logic exists.
P010 Score ≥70, multi-signal, no protection flags → WASTE Match AWS's ≥70/≥80 TERMINATE tier and Azure's now-matching thresholds implement this band correctly, modulo the P001/P002 protection gaps above already noted.
P011 Score 50–69, or single strong signal → REVIEW Match AWS's REVIEW_RESIZE band (≥50 prod) and dev/staging's own tier structure land here correctly for the numeric-threshold part of this rule.
P012 Score <50, no strong pattern → KEEP Match KEEP is the correct fallthrough on both clouds below every other band.

PROD_AUTO_WASTEFALSEMissingSpec's intent — prod WASTE needs a separate execution-approval gate before deletion — has no code equivalent. action=TERMINATE is the direct classifier output; there's no downstream approval step in the provider layer.

SCORE_BANDS_ARE_CUMULATIVEFALSEMatchEach signal category (CPU, memory, network, disk I/O) picks its own single highest band via if/elif — matches spec's intent exactly.

What this means for closing it today

  • AWS is close to spec-compliant on the numbers — the scoring tables match almost exactly, with the real code layering on a few extra fine-grained bands the spec doesn't mention. Safe to say "AWS matches the documented scoring model."
  • Azure's numbers don't match the spec — different CPU thresholds, no memory/network/disk-I/O signals at all, and a flat +50 base on stopped VMs the spec never describes. This isn't a rounding difference, it's a materially different scoring model. Don't sign this off as compliant without flagging it explicitly.
  • Five of twelve rules (P002, P003, P004, P007, P008) aren't implemented at all — no HA/DR protection, no scheduled-workload exemption, no lookback gating, no seasonality handling, no ASG/VMSS group awareness. These are the rules that make the spec's own test scenarios (5, 6, 7, 8, 9, 17, 18) resolve correctly — right now several of those scenarios would misclassify against real code.
  • Two Rule_Configuration parameters were fixed today on Azure — STOPPED_WASTE_DAYS (was hardcoded to 30, now 60, matching AWS and spec) and MISSING_DATA_COUNTS_AS_WASTE (was adding +10 for missing CPU data, now 0). AWS already matched both natively — the earlier draft of this audit wrongly said AWS also violated the missing-data rule; it doesn't, confirmed by reading _compute_waste_score() directly.
  • The retention exemption (P001) is real, verified progress — but still only implemented for stopped/deallocated instances, not running ones, on either cloud.
  • PROD_AUTO_WASTE's intent — a separate approval gate before any destructive action — doesn't exist in the provider layer at all. Worth confirming with jatinder whether that gate lives elsewhere (frontend confirmation dialog, a runbook step) before treating this as a gap; the audit can't see past the classifier.
